# Execute the coordinator prompt

Execution means OpenCode coordination through Orca orchestration. Prompt generation alone never authorizes execution. Use the installed orchestration skill if available, subject to the user's skill permissions. Its version-matched runtime guide is authoritative for commands and lifecycle behavior.

Resolve the CLI once: use ORCA_CLI_COMMAND if set; otherwise orca-dev in a dev session exposing ORCA_DEV_REPO_ROOT; otherwise orca-ide on Linux outside an Orca-managed terminal; otherwise orca. Never invoke bare orca on unmanaged Linux, where it may be the GNOME screen reader. Reuse the selected executable; if it fails, report the exact error rather than switching builds.

Load `<selected executable> skills get orchestration` before runtime actions. Load its coordinator-loop reference for model selection/DAG work, placement-and-remote reference for server placement, and recovery-and-cleanup reference only if needed. Resolve unknown flags with installed help. If the guide is unavailable, perform only supported read-only discovery and report the missing capability; do not invent commands. A runtime_access_denied error requires sandbox escalation, not a runtime restart.

In Plan, verify project location, host, cwd, the current model catalog, supported backends, cost/provider limits, and resources. Resolve missing requirements through numbered questions with suggested defaults and reasons. Unanswered defaults are unresolved. Present the task and agent assignment summary required by SKILL.md: explain how the subtasks achieve the goal, why each agent/model was chosen, and how dependencies determine parallel work and execution order. Include the task table, acceptance checks, cost/resource limits, and permission scope. Ask for explicit approval and wait before entering Build, creating a Run, or dispatching workers. Resolved requirements and accepted defaults do not approve this summary. Revise and obtain approval again when the user requests changes or later changes affect the plan; unchanged approved assignments need no repeated approval. Mode switching must use supported controls; request the required UI action if necessary. Do not dispatch while still restricted to Plan.

Before dispatch, apply and verify the broadest supported task/session permissions for OpenCode and each worker backend. Use the installed guide's actual controls, not guessed flags. Preserve platform-required approvals and confirmation for destructive or external actions. No commits/pushes without explicit request. Collect necessary permission prerequisites up front where possible; do not weaken unrelated global settings or assume permissions propagate to workers. Report unsupported elevation honestly. If the execution host is wrong, resolve correct server setup instead of changing placement semantics.

Create the Run through orchestration run-create; create tasks/attempts through orchestration worker-start using supported model, workspace, and permission arguments. Use explicit dependencies where needed. Keep returned IDs and receipts, and start the independent resolved wave before waiting. Default to one attempt per task unless the user changed that limit during Plan. A failed start may leave resources: inspect its receipt; do not automatically relaunch.

Supervise through Orca's mailbox and worker records. Follow acknowledgment and settlement rules, including matching completion to the active Dispatch and checking acceptance artifacts. Consolidate workers' unresolved requirements into focused numbered user questions. Timeout, missing output, and lost contact do not prove exit. Do not retry, abandon, stop, or release solely because observations are unavailable. Workers must follow their injected preamble for heartbeat, check, ask, and worker_done commands and outcome fields.

After accepted settlement, release each worker, or record explicitly authorized retention/reuse according to the guide. Investigate uncertain cleanup through receipt recovery instructions; do not force-close terminals. Finish when expected attempts have explicit outcomes and cleanup decisions, or report a concrete blocker with unresolved lifecycle state. Report Run/Task/Dispatch IDs and evidence without claiming unobserved execution or Mobile behavior.
